## 为什么要有这个站

写 DSH 插件的文章有个特点：同一批插件被翻来覆去地讲，名字还不一定一致。有的叫 `dsh-web-ui-all`，有的叫 `@linxin666/dsh-web-all`，其实是同一族东西；有的把收费、免费、内测的口径混着写。

把这些文章一篇篇收藏，等于把混乱原样搬进收藏夹。所以本站的做法是：**顺着文章发现插件，再回到它的官方 GitHub 仓库读 README，把内容整理成卡片**。文章只是「发现来源」，正文以官方说明为准。

## 收录范围：只收需要额外安装的插件

官网开箱就带的 Subagents、Terminal、Agent loop、网页搜索，以及 Standard / Code / Minimal / Creator 四种运行模式，**一律不建条目**——不用装、也没法单独装，混进「值得装什么」的清单里只会添乱。官网界面里标为 Experimental 的内置项同样不收。

判断标准只有一条：**这个东西要不要你自己动手装一次？** 要，才收录。

## 内容从哪来

1. **发现**：公众号、社区目录、官方文档里看到某个插件，顺着它的名字和描述去 GitHub 找官方仓库。
2. **核实**：打开仓库 README，确认它确实是这个插件、怎么装、能干嘛。
3. **整理**：把简介、安装命令、功能亮点写成卡片，仓库地址挂上，原文链接作为「参考文章」放侧栏——**不照搬文章正文，只参考补充**。

本站**不替插件写宣传稿**，也不渲染任何单篇文章的原话；插件介绍以上方官方仓库为准。

## 三层结构

| 层 | 文件 | 作用 |
| --- | --- | --- |
| 来源台账 | `data/sources.yaml` | 一篇文章 / 一个目录一条：标题、发布方、原文链接、日期（没有就写「待补」）、在本站的角色 |
| 插件主档 | `data/plugins.yaml` | 一个插件一条：名字、别名、分类、`repo`（官方仓库）、安装方式、README 整理的简介与功能亮点，以及 `refs` 参考来源 |
| 分类 | `data/categories.yaml` | 分类口径与说明 |

`python3 tools/build_data.py` 会校验引用完整性（引用了不存在的来源直接报错）、算每个插件的参考文章数与仓库确认数、生成插件页 / 来源页 / 搜索索引 / 首页统计，然后 `hugo --minify` 出静态站。

## 徽章怎么来的

- **官方仓库已确认**：已链到 GitHub 仓库，内容按 README 整理。
- **仓库待确认**：暂未找到官方仓库，内容待补全。
- **提示**：名称 / ID / 兼容性还需读者留意，例如「与另一个插件名称相近，勿混」「社区项目，非官方」。

## 加一篇新文章（三步）

1. 在 `data/sources.yaml` 末尾加一条，`id` 用短横线小写（如 `wx-plugin-2026-11`），把原文链接贴进 `url`。
2. 打开 `data/plugins.yaml`：文章提到的插件如果已有条目，把来源 `id` 加进它的 `refs`；确实没见过的才新建条目，中文名 / 英文名 / 包名都塞进 `aliases`。然后**顺着名字去 GitHub 找官方仓库**，补上 `repo` / `install` / `summary` / `features`（按 README 写，不抄文章）。**官方开箱即用的内置能力不要新建条目**（生成脚本会直接拦下）。
3. 跑 `python3 tools/build_data.py && hugo --minify`，然后提交生成出来的 `content/plugins/`、`content/sources/`、`static/search.json`、`data/derived.json`（这四个是产物，但**要一起进 git**，这样线上构建只需要 Hugo，不必装 PyYAML）。
